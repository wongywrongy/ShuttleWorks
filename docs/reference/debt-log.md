# Debt Log

The **visible backlog** the code-health practice feeds (`CODE_HEALTH.md` #6):
when a change spots debt outside its own scope, it lands here instead of being
silently fixed (scope creep) or silently dropped. Each entry: **what · where ·
why it matters · rough size**. Add rows as debt is found, move rows to
**Closed** as it is cleared, and keep it honest so "the log growing faster than
it shrinks" stays a real signal — that is the trigger to run another bounded
program, per `CODE_HEALTH.md`.

**Keep entries short.** An entry earns its length only when the *decision* is
hard to state; the narration of how it was found belongs in the commit or the
audit doc it came from. A log nobody reads is the same as no log.

**Reconciled 2026-08-29.** Open entries were checked against the code after the
performance/refactor and production-parity demo programs. Stale implementation
claims were corrected and completed work was moved to **Closed**. Historical
program plans remain recoverable from Git; this file tracks only live debt.

**`auth_throttle` grows without bound and retains raw addresses** (found by the SP-REORG-1 review pass, 2026-08-19; pre-existing — the extraction to `core/throttle.py` moved the code verbatim and changed none of this)
- **Rows are never deleted.** `throttle_record_attempt` resets `failures`/`window_started_at` in place and `throttle_check` only reads; nothing in the tree issues a DELETE against `AuthThrottle`. The table therefore holds one row per throttle key **ever seen**, forever: `ip:` / `entry:` / `eip:` per client address, `account:` / `eacct:` per email address. Growth is O(distinct IPs + distinct addresses ever attempted), and a public entrant tier is exactly the surface that makes that number large.
- **The key is the primary key and it is plaintext.** `auth_throttle.key` is a `String(200)` holding e.g. `eacct:parent@example.com`. A *failed* sign-in creates the row, so the table accumulates addresses that have **no account** — it is a permanent, unhashed log of every address anyone ever tried, in a product that otherwise scopes PII deliberately (the entrant tier keeps name, club and birth year out of URLs precisely to avoid this class of retention).
- Two independent fixes, either useful alone: prune rows whose `window_started_at` is older than the longest window and whose `locked_until` has passed (a cheap periodic DELETE, and the columns to do it already exist); and key the account namespaces on a digest rather than the address, which costs nothing because the key is only ever compared for equality. **A retention ruling is owed** alongside D7's entrant-erasure question — they are the same question about different tables. S each.

## Recorded deliberately — not defects, not scheduled

Kept so a future reader doesn't rediscover them as bugs.

- **The public entrant origin trusts `challenges.cloudflare.com` on `/e/signup`, and only there.** The nginx `map` scopes that exception to the signup route. The operator console now runs on a separate origin and does not inherit this trust.
- **No in-product off-site durability in local mode.** `tournament_backups` rows live in the same database as the data they protect, so a lost disk loses both. Local mode is one operator on their own machine, where off-site copies are their responsibility exactly as for any desktop application, and `install-local.md` says so. Cloud mode has a real answer in `install-selfhost.md` (`pg_dump` + `pg_dumpall --globals-only`, encrypted, off-host, monthly restore drill). Revisit only if local mode stops being single-operator.
- **The entrant tier has no password-visibility affordance, deliberately.** `TextField` gives every `type="password"` a "Show password" toggle driven by `onClick`; the account forms remain complete without hydration, so a control that depended on an unrelated module would be misleading. It is opted out with `revealable={false}`. The prohibition is derived, not spelled: `login.test.ts` fails any `<button type="button">` in the login, signup or entry documents. This does not prohibit the bounded same-origin route modules used by My Entries, entry progress, player filtering, or bracket paths.
- **The CSRF form channel depends on a Starlette internal.** `apps/api/src/core/form_csrf.py::form_csrf_proves` reads the request body inside the middleware, and the only thing keeping the downstream route from receiving an **empty** form is `starlette.middleware.base._CachedRequest.wrapped_receive` replaying `request._body`. A private attribute of a private class, verified against Starlette 1.3.1. If a future upgrade changes that replay branch, every urlencoded route behind the middleware silently receives a blank body — the entry form would accept submissions with no players. Mitigation in place: `tests/backend/test_form_csrf_channel.py` asserts an eight-player ~20 KB submission on **stored rows**, so the breakage is a red test rather than quiet data loss. **Grep for `wrapped_receive` before bumping Starlette.**
- **`bracket_results.reason` is not mirrored anywhere** — obsolete rather than fixed. The Supabase mirror was removed entirely in SP-CLOUD-3 (ADR 0012); `sync_service.py` is deleted and `sync_queue` was dropped in migration `p9a3b7c1d5e6`. Local SQLite persists `reason` (migration `k4a7b1c9d3e5`) and the UI reads the local API, so nothing was ever user-visible. Recorded so the entry's disappearance does not read as a silent fix.
- **`StandingRow`'s counter fields are optional in the OpenAPI schema and required in TypeScript — and that is correct.** `bracket/standings.py::StandingRow` is a stdlib dataclass whose eight counters carry defaults, so pydantic emits them as non-required in `components.schemas`; `openapi-typescript` nonetheless renders them as **required with `@default` doc tags**, and the backend always emits all nine fields. So the console alias (`bracketDto.ts::StandingRowDTO`) needs **no `Required<>` wrapper** and the entrant mirror needs no compensation — the generated type is honest as-is. Recorded because the mismatch looks like drift on inspection and an earlier draft of the SP-DM-3 P1 plan assumed a wrapper would be needed. Converting the dataclass to a `BaseModel` with required fields would make the schema literally match, at the cost of putting pydantic next to the `scheduler_core` domain types; not worth it for a difference no consumer can observe.
- **`DISPLAY_PRESETS` / `getPreset` / `DisplayPreset`** are kept for the future venue-preset picker (product decision 2026-07-01). knip keeps flagging them; expected.
- **`slotToTime` / `formatSlotTime`** is an intentional alias (~20 call sites each). Renaming is cosmetic churn with no behaviour benefit.
- **8 dto types read "unused" to knip and are kept on purpose** — `CourtClosure`, `SoftViolation`, `AvailabilityWindow`, `PlayerImpact`, `SchoolImpact`, `MetricDelta`, `ProposalKind`, `SuggestedAction`.
